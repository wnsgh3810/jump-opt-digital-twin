## 핵심 패턴

### 1. 단편적 fix 거부, 본질적 분석 선호
- **시그널**: "실제 현실이랑 맞지 않는 억지로 제한하는 거는 안될거 같애", "냉철히 분석 비판해봐"
- 작은 영역만 마스킹하거나, 파라미터를 비물리적 값으로 강제하는 등의 hack을 거부
- **How to apply**: 모델/식이 안 맞을 때 "여기만 무시" 같은 제안 금지. 항상 근본 원인 분석부터 시도. 근본 원인이 모델 구조 문제로 드러나면 모델 자체를 수정하거나 한계를 명시적으로 인정.

### 2. "다 해보자" — 분기점에서 선택지 모두 탐색
- **시그널**: "다 해보자", "전부 해보자"
- Claude가 A/B/C 옵션을 제시하고 추천을 하면, 우선 작은 sanity check부터 차례로 다 돌리고 그 다음 본 작업 — 이 시퀀스를 자주 채택
- **How to apply**: 옵션을 제시할 때 "어느 게 빠를지" 추천만 하지 말고, "이거 하면 X 알 수 있고, 저거 하면 Y 알 수 있음" 식으로 각 옵션의 정보 가치를 명확히. 사용자가 "다 해보자" 하면 sanity → 본 분석 순서로 진행.

### 3. 직접 데이터 cross-check
- **시그널**: 갑자기 데이터의 의미를 본인이 검증하는 질문 — 예: "ddz는 속도 아니까 dz알 수 있잖아 그거 미분하면 되는거 아냐? Real data에서?"
- 분석 결과를 그냥 받아들이지 않고, 데이터에서 직접 검증 가능한 지점을 찾으려 함
- 단위, 부호, 측정 가능 여부 직접 확인
- **How to apply**: 결론을 던질 때 "real data에서 어떻게 확인할 수 있는지"까지 같이 알려주기. 그리고 측정값과 derived값 구분 명시 (real data엔 q, dq, tau, GRF만 있음 — z/dz/ddz는 kinematic 가정 필요).

### 4. 본질적 방향 선택
- **시그널**: "B로 가자 범위도 합지적으로 키우고" 류
- A/B/C 옵션 제시 시 — 단편적 fix(A)보다 본질적이지만 더 비싼 방법(B)을 자주 선택
- "범위도 합리적으로" — 검색 범위가 좁아서 진짜 답이 빠진 가능성도 함께 챙김
- **How to apply**: 선택지를 줄 때 "더 빠른 옵션"과 "더 본질적인 옵션"을 구분해 제시. 사용자는 본질을 자주 택함.

### 5. 비판적 자기 검증 요구
- **시그널**: "반복해서 오래 고심하고 냉철하게 분석 비판해봐", "비판적 분석"
- Claude의 결과를 그대로 받지 않고, 비판적 재검토를 요구
- **How to apply**: 분석 결과를 낼 때 자체적으로 "근거가 약한 부분", "대안 가설", "이게 틀렸을 가능성"을 함께 제시. 결과만 던지지 말 것.

## 디테일 검수 습관
- 단위/부호/물리 컨벤션 cross-check (Av·c1·ddz가 한쪽으로 옮겨질 수 있는지 등)
- M_tot 계산, alpha 곱셈, output vs input 토크/에너지, RK4 alpha 버그 등 Claude가 놓친 미세 오류 직접 발견
- **How to apply**: 코드 작성 후 항상 단위/부호 self-check 한번 더. 사용자가 종종 잡아냄.

## 의사소통
- 한국어로 소통, 직설적이고 짧게
- 긴 설명보다 표/리스트로 정리된 결론 선호 (스크린샷 보면 모두 표/bullet 형태)
- 원인 → 해결책 → 다음 단계 순서로 정리하면 잘 받아들임
